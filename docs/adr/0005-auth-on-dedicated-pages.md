# Log in and register on dedicated pages

The tabbed login/register dialog is replaced by two routes, `/login` and `/register`. A page that holds exactly one form lets password managers tell a sign-in form from a sign-up form, can be linked to (the route guard and the expired-session handler send users to `/login?redirect=…`), and keeps each form's error state separate. Together with the move we settled how accounts are identified at login and how forms report errors and successes across the whole app.

## Decisions

- **Registering logs the user in.** `POST /Auth/Register` returns `{ jwtToken }` exactly like Login. No email confirmation is required, so there was nothing to wait for; asking for the password a second time or making two requests from the client were rejected.
- **Login accepts a username or an email, told apart by `@`.** Usernames may only contain Latin letters, digits and underscores (`AllowedUserNameCharacters`), so an identifier containing `@` is always an email and anything else is always a username. The alternative, trying the email lookup and then the username lookup, would make the result depend on lookup order as soon as one account's username equals another account's email. `AllowedUserNameCharacters` stays in Identity even after request validation moves to FluentValidation: it guards every write of a username, not one request shape. Do not allow `@` in usernames without replacing this scheme.
- **One wrong-credentials message.** "Incorrect username, email or password." never says which part was wrong. Registration already reveals whether a username or email is taken, so this isn't hiding much; it is kept because it is the convention users and password managers expect.
- **Error messages: field errors at the field, the banner only for the rest.** The form-level banner shows only what can't be shown next to a field (wrong credentials, network or server failure, field errors for fields the form doesn't have). It never repeats a message that's already shown under a field. Toast-only callers still get the full message. Every message is a whole sentence that names the field and says how to fix it.
- **Success messages.** Success is reported with one toast titled "<Noun> <past-tense verb>" (for example "Tournament created") and a full-sentence detail, never with both an inline banner and a toast, never with "successfully!", and always in the glossary's terms. Auth pages show no success banner: after logging in, the header showing the username is the confirmation.
- **Eager validation on every form.** A field is first validated when the user leaves it (lazy). Once it is invalid, it is validated on every keystroke (aggressive) until it's valid again, so an error disappears the moment it is fixed but doesn't appear while the user is still typing. VeeValidate v4 removed its "interaction modes" and `configure()` only takes fixed true/false triggers, so this can't be a global setting. Instead every field binds its listeners through the shared `eager()` helper in `frontend/src/includes/validation.js`. Do not "simplify" this back to `validateOnInput: true`: that shows "must be at least 3 characters" after the first keystroke.
